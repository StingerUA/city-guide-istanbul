## Шаг 1. Применить миграцию в своём Supabase

Проект: `https://qfohfbuwnpjcbhmyosaf.supabase.co`

1. Перейти в [Supabase Dashboard](https://supabase.com/dashboard), выбрать нужный проект.
2. В **SQL Editor** создать запрос из `supabase/migrations/20261012_0001_initial.sql`.
3. Внимательно сверить проект и текст SQL; выполнить миграцию **один раз**. Не вставлять в Supabase прежние `drizzle/*.sql` — они рассчитаны на SQLite.
4. В **Database > Tables** проверить таблицы с префиксом `cg_`.
5. В **Storage** проверить приватный bucket `city-guide-photos`. Он не публичный, а политики загрузки/выдачи появятся в следующем этапе.
6. В **Authentication > Providers > Email** включить подтверждение email (не отключать ради обхода ошибок входа).
7. Проверить, что **оба администраторских email подтверждены в Supabase Auth**. Регистрация такого email сама по себе не даёт админ-доступа, если адрес не подтверждён.
8. Для массовой регистрации настроить **Custom SMTP** в Authentication: иначе ограничения встроенной почты могут мешать регистрациям.

Пока запись в базу через браузер преднамеренно запрещена: RLS настроен на чтение в пределах роли. Для изменений потребуются валидирующие RPC либо серверные операции с проверкой прав. Никаких универсальных SECURITY DEFINER SQL-исполнителей создавать нельзя.

## Шаг 2. Переменные для Cloudflare

На сервере Worker (после завершения перехода API) должны быть переменные:

```env
SUPABASE_URL=https://qfohfbuwnpjcbhmyosaf.supabase.co
SUPABASE_PUBLISHABLE_KEY=sb_publishable_...  # вставить своё значение из Settings > API Keys
```

Они НЕ являются ключами с привилегиями администратора БД. Для локальной проверки скопировать `.env.example` в `.env.local` и заполнить ключ. Файл `.env.local` игнорируется Git.

Для будущего прямого браузерного Supabase SDK можно задать также `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`; сейчас авторизация выполнена через серверный HTTP API и браузеру ключ не нужен.

**Не добавлять:** пароль PostgreSQL, `sb_secret_...`, legacy `service_role`, SMTP пароль, Cloudflare API token — ни в GitHub, ни в сообщения чата.

## Шаг 3. Диагностика (после деплоя)

Открыть `https://<worker>.workers.dev/api/supabase/status`.

- `{"configured":true,"connected":true}` — Worker смог обратиться к Supabase Auth, **не** означает готовность всей базы и бронирований.
- `{"configured":false,"connected":false}` — переменные не переданы / некорректны.
- `{"configured":true,"connected":false}` — сеть/ключ/проект недоступны.

Вход: `/signin`; админ `/admin`; партнёр `/partner`; клиент `/tourist`. Однако реальная работа кабинетов и сохранение данных останутся недоступны до замены D1/R2.

## Почему не использован секретный ключ

`sb_publishable_...` — публичный ключ; защищает не сам по себе, а совместно с пользовательскими токенами и RLS. Привилегированный `sb_secret_...` здесь не требуется и не должен передаваться в браузер. В этой ветке присутствует только клиентская аутентификация и безопасная схема с запретами по умолчанию.
