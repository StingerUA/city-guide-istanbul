# City Guide: перенос в GitHub, Cloudflare и Supabase

План подготовлен 10 октября 2026 года. Репозиторий:
https://github.com/StingerUA/city-guide-istanbul

## Что уже сделано

Исходники загружены в GitHub. В версии v0.2.2 убраны переключатель кабинетов
и служебные надписи о пилоте, домене и платных подключениях. Главная ссылка
ведёт к клиентскому интерфейсу. Уменьшено нижнее меню, скрыты отели,
добавлены изображения ночной жизни, истории и природы.

В серверном коде администраторы определяются только по двум email:
`nncdecdgc@gmail.com` и `sayitatas@hotmail.com`.
Email должен поступать от проверенного сервиса авторизации. Поле email в
форме профиля не даёт прав. Первый посетитель больше не становится администратором.

Текущий код ещё использует авторизацию прежнего размещения, D1 и R2.
Подключение Supabase, миграции PostgreSQL и конфигурация самостоятельного
размещения Cloudflare пока не реализованы. Этот документ — порядок следующего
этапа, а не подтверждение завершённого переноса работающего приложения.

## Целевая схема

| Сервис | За что отвечает |
| --- | --- |
| GitHub | Исходники, история изменений, обновления |
| Cloudflare Workers | Интерфейс приложения, серверные API, адрес приложения |
| Supabase Auth | Регистрация, вход, подтверждённые аккаунты |
| Supabase PostgreSQL | Профили, заведения, заявки, отзывы, акции и обращения |
| Supabase Storage | Фотографии, загруженные заведениями |

Для начала можно использовать адрес Cloudflare вида
`https://<имя-приложения>.<аккаунт>.workers.dev`. Собственный домен для этого
не требуется. Конкретная ссылка появится после создания Worker.

После переноса адреса будут такими:

- `/` и `/tourist` — клиентская версия;
- `/admin` — кабинет двух администраторов;
- `/partner` — кабинет одобренных партнёров.

Знание адреса кабинета само по себе не даёт доступа.

## Шаг 1. Создать Supabase — можно сделать сейчас

1. Открой https://supabase.com/dashboard и войди в свой аккаунт.
2. Создай проект `city-guide-istanbul` в организации на тарифе Free.
3. Выбери доступный регион поближе к Турции. Сохрани пароль базы у себя.
4. Дождись готовности проекта.
5. Открой **Connect**: там доступны Project URL и Publishable key.
   Все ключи также находятся в **Settings → API Keys**.
6. Для подключения приложения понадобятся Project URL и публичный ключ
   вида `sb_publishable_...`. Их можно передать разработчику.

Пароль базы, `sb_secret_...`, старый `service_role`, токены Cloudflare и SMTP
сохраняются в секретах соответствующих сервисов. В исходники и переписку
их добавлять не нужно.

## Шаг 2. Подготовить Cloudflare — можно сделать сейчас

Войди на https://dash.cloudflare.com и открой **Workers & Pages**.
Пока достаточно аккаунта на бесплатном тарифе. Подключение конкретного
репозитория к автоматической публикации выполним после адаптации кода.

GitHub уже хранит проект. GitHub Pages для этой архитектуры не используется:
серверная часть будет работать в Cloudflare Workers.

## Шаг 3. Адаптировать приложение — следующий этап разработки

В коде потребуется:

1. Добавить вход и регистрацию через Supabase Auth, проверку подтверждённого
   email и серверную проверку сессии. Заменить `/signin-with-chatgpt` и
   `/signout-with-chatgpt`. На самостоятельном Worker нельзя доверять
   входящим заголовкам `oai-authenticated-user-*`: вне прежнего шлюза
   их может прислать сам посетитель.
2. Переписать обращения к D1/SQLite на Supabase/PostgreSQL. Подготовить
   отдельные миграции PostgreSQL. Файлы из `drizzle/` сейчас относятся к
   SQLite; запускать их в SQL Editor Supabase без преобразования нельзя.
3. Настроить RLS: клиент получает свои заявки и профиль, партнёр — свои
   заведения и связанные заявки, администраторы — разрешённые им данные.
   Роли нельзя брать из редактируемых пользователем метаданных.
4. Перенести загрузку и выдачу фотографий с R2 на Supabase Storage.
   Для неопубликованных изображений сохранить ограничение доступа.
5. Перенести проверку доступности и создание бронирования в атомарную
   транзакцию/функцию PostgreSQL. Сохранить защиту от повторных заявок.
6. Подготовить самостоятельную конфигурацию Cloudflare, команды сборки и
   публикации, убрать обязательную зависимость от окружения Sites.

Адрес Supabase и публичный ключ подключаются через настройки окружения.
Если для отдельной серверной операции понадобится привилегированный ключ,
он хранится только в Cloudflare Secrets; клиентский код его не получает.

## Шаг 4. Решить вопрос с уже введёнными данными

ZIP и GitHub содержат код и демонстрационные изображения. Рабочая база
и загруженные пользователями фотографии в архив исходников не входили.

Если созданные в старом приложении записи нужны, перед переключением
понадобится экспорт базы и файлов, преобразование SQLite → PostgreSQL,
сопоставление старых ID пользователей с ID Supabase Auth и обновление
ссылок на изображения. Отзывы, заявки и владение заведениями должны
сохранить связи. Права администратора заново проверяются по разрешённым email.

Если реальные данные ещё не вводились, можно начать с новой базы и
отдельно загрузить демонстрационный каталог.

## Шаг 5. Настроить вход и письма

После появления адреса Cloudflare добавим его в настройки Site URL и
разрешённые redirect URL в Supabase Auth. Будут проверены вход, выход,
возврат в нужный кабинет и восстановление доступа.

Для регистрации по email требуется настроить Custom SMTP. Стандартный
почтовый сервис Supabase ограничен адресами участников команды проекта
и не подходит для отправки писем всем партнёрам и клиентам. Можно
использовать отдельного SMTP-провайдера; его стоимость и лимиты проверяются
при выборе. Пароли от почты в репозиторий не добавляются.

## Шаг 6. Подключить GitHub к Cloudflare и опубликовать

После выполнения шага 3:

1. В Cloudflare Workers подключить GitHub и дать доступ к
   `StingerUA/city-guide-istanbul`.
2. Выбрать ветку `main` и корень репозитория.
3. Указать команды сборки и публикации из подготовленной конфигурации.
   Точные команды будут добавлены вместе с адаптацией; текущая сборка
   ещё рассчитана на прежние серверные зависимости.
4. Добавить настройки Supabase в окружение сборки/Worker, а секреты —
   в Secrets, согласно тому, где их будет читать новый код.
5. Запустить первую публикацию и сохранить адрес `workers.dev`.

При включённой Git-интеграции дальнейшие push в настроенную ветку могут
автоматически запускать сборку и публикацию.

## Шаг 7. Проверить новое размещение

Проверим вход обоих администраторов, отказ постороннему пользователю,
изоляцию двух партнёров, сохранение профиля, фотографии, каталог,
заявки и отзывы, а также интерфейс на телефоне на RU/TR/EN.
Реальные платежи подключаются отдельной задачей: текущие заявки остаются
тестовыми и не списывают деньги.

## Расходы на старт

По официальным тарифам на дату подготовки:

- Supabase Free: 500 МБ базы, 1 ГБ файлов, 50 000 активных пользователей
  в месяц. Есть ограничения передачи данных; неактивные проекты могут
  приостанавливаться через неделю.
- Workers Free: 100 000 запросов в день, 10 мс CPU на вызов. При сборке
  и проверке нового сервера нужно убедиться, что приложение укладывается
  также в лимиты выполнения, а не только в число посетителей.

Начать можно на бесплатных тарифах. Это не обещание бесплатной работы
при любой нагрузке; отдельно учитываются почта, объём фотографий и лимиты
сервисов. Оплачивать домен на первом этапе не требуется.
